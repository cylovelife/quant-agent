## 字段和缺失语义

基础特征共94项：D类9、E类20、I类9、M类18、P类13、S类12、V类13。数据说明提到 MOM 前缀，但本次文件没有该组。训练特征共有137,675个缺失单元格，没有整列全缺失的特征。本轮保留缺失值，尚未拟合填补器、缩放器或特征选择器。

三项训练专有字段为 `forward_returns`、`risk_free_rate`、`market_forward_excess_returns`。它们都有完整有限值，但不能作为同一行的预测输入。

尤其需要区分：官方 `market_forward_excess_returns` 是对前瞻收益减去滚动五年均值并进行 MAD 限幅的字段，不应直接等同于 `forward_returns - risk_free_rate`；后者用于官方评分中的超额收益计算。

演示测试提供这三项的一步延迟列 `lagged_*`。本次逐行核对得到：

- 10行演示特征均与 TRAIN 中相同 date_id 的94项基础特征一致。
- 每组 `lagged_*` 均与前一个已观察 date_id 的对应训练字段一致，最大绝对差为0。
- `is_scored` 原 CSV 为字符串 `true/false`，实际9行true、1行false。必须显式解析，不能使用会把非空字符串 `"false"` 转成真的通用布尔转换。

真实文件的演示测试只有10行，不能把数据页对原公开测试180个 date_id 的说明当作当前文件行数。演示输入与训练重叠，不能作为独立泛化测试；本次不报告其投资表现或评分。

## 顺序接口和原评估 API 验收

新增 [sequential.py](../../src/quant_agent/competitions/hull/sequential.py) 每次只接受一行，严格要求 date_id 递增，并将99列输入拆分为：

```text
日期标识和评分元数据：date_id、is_scored
模型可见特征：94项基础特征 + 3项 lagged 字段
模型不可见：当日三项训练专有字段
```

回调只能取得97项特征；`date_id` 与 `is_scored` 不进入模型。输出须为有限数值标量且在0–2范围内。false评分行也必须生成预测，不能删除该行或改变后续调用顺序。适配器的 `reset()` 重置序号与调用计数；回调约定为无可变历史状态的已拟合函数，后续若使用有状态模型，还需要单独定义模型状态的重置。

[api_check.py](../../src/quant_agent/competitions/hull/api_check.py) 直接加载下载包的原 `DefaultInferenceServer` 和 `DefaultGateway`，运行本地 gRPC 推断，并核对官方写出的 `submission.parquet`。在两个新进程中分别通过：

- 每轮10次调用、每批1行，覆盖10个原始date_id。
- 全部输出配置1.0；官方文件列为 `date_id,prediction`，原序一致。
- 两个新进程的输出表逐项相同，未继承上一轮适配器状态。
- 99列原输入传入接口，业务回调只读取97项特征。

首轮成功 API 内部计时约7.23秒，只代表这10行演示和本地通信，不代表完整训练或平台隐藏评测耗时。结果位于本地 `api-function-1/api_result.json`、`api-function-2/api_result.json` 与 `acceptance.json`。该验收不是线上提交，也没有恢复已结束赛事的参评资格。

## 官方评分与边界

官方 metric v3 的代码按原字节纳入 [_official_metric_v3.py](../../src/quant_agent/competitions/hull/_official_metric_v3.py)，SHA 仍为 `2f75bc0b1602afd3dd3d7da3415841c98ef49639b10d6dd53d261ea612c80ae6`。来源和 Apache-2.0 范围分别见 [NOTICE](../../src/quant_agent/competitions/hull/OFFICIAL_METRIC_NOTICE.md) 和 [LICENSE](../../src/quant_agent/competitions/hull/OFFICIAL_METRIC_LICENSE.txt)。该许可不扩展到原投资系统或其他项目代码。

本地 [metrics.py](../../src/quant_agent/competitions/hull/metrics.py) 在调用前核对长度、date_id原序、数值类型、NaN/Inf和配置范围，并复制输入，避免官方函数修改调用方的数据。对完全恒定的市场收益显式拒绝，防止浮点舍入产生极小非零标准差后得到误导分数。不可评分与得分为0分别记录。

官方评分使用超额收益的几何日均值和策略收益标准差，并施加波动与收益惩罚。0–2是配置硬边界，市场1.2倍波动是评分惩罚阈值，两者不同。负分区间中，除以更大惩罚也可能使数值更接近0，因此不能只凭分数排序判断风险更低。

| 开发窗1 | [7536, 8040) | 503行，7536–8038 |
| 开发窗2 | [8040, 8544) | 503行，8040–8542 |
| 较新保留窗 | [8544, 9048) | 未评分 |

标签可用时点按下一条实际观察的 date_id 记录，训练和评分标签均须在边界前严格成熟。因此每个开发窗末尾一行被排除；末条训练记录缺少下一观察时点，也不推定标签已成熟。每个窗的历史拟合区间可用行数分别为7,535和8,039，但本次常数参考不需要拟合。

| 固定配置 | 开发窗1官方评分 | 开发窗2官方评分 | 策略/市场波动比，窗1 / 窗2 |

最终结果位于 `constants-20261029-verified/results.json`，源码/依赖/输入和协议哈希位于同目录 `frozen.json`，缺失明细位于 `audit.json`。波动比的独立计算保存在 `constants-20261029/volatility_diagnostics.json`。

## 依赖隔离与已解决问题

在独立worktree `hull-baseline-20261029/quant-agent`、分支 `codex/hull-baseline-20261029` 中开发，使用单独 `.venv`。主工程仍为此前 GitHub 已同步的版本，本轮不切换冻结投资实验的运行版本。

[requirements-hull.txt](../../requirements-hull.txt) 复用原开发依赖，新加评估 API 需要的四类库；[requirements-hull.lock](../../requirements-hull.lock) 以原 `requirements.lock` 为约束，带下载哈希锁定45个依赖。原锁文件和原环境未修改。

两项真实接口故障已解决：

1. 首次解析的 PyArrow 26.0.0 在 import 时要求 NumPy 2；包元数据兼容检查未发现此冲突。Hull环境改为实测可导入的 PyArrow 19.0.1，保留项目 NumPy 1.26.4。
2. 官方 `define_server()` 只接受具名普通函数，拒绝对象方法。入口增加具名 `predict()`，再委托给适配器；没有修改原评估 API。

环境修复前后及最终源码冻结后，固定常数结果逐项一致。这几次属于复现，不是新的独立样本，也没有进行候选搜索。首次失败目录保留，最终成功结果使用新目录，不覆盖失败证据。
